\section{Type Inference}\label{sec:type-inference-new}

In this section, we describe our type inference algorithm, where the goal is to annotate each subexpression of a program with its most precise type. Specifically, we describe our type inference algorithm for expressions with float type $\float[B;V]$, showing how \Slice{} populates the cut set $B$ and value set $V$ for each expression, as these refinements determine how and whether the expression can be discretized. Type inference for all other types is standard and follows the classic Hindley-Milner type inference algorithm. For our type inference algorithm on float-typed expressions, we follow a standard two-phase approach: the first phase traverses the program once to generate a set of type constraints over unknown types; the second phase solves these constraints to produce a fully annotated program.

\subsection{Constraint Generation}

We use a rich constraint language, shown in Figure~\ref{fig:constraints-grammar}, to express requirements over type structure and float refinements. As we want \Slice{} to propogate information about control flow-relevant thresholds and possible value ranges, our syntax is over $B \in \cutsets$ and $V \in \valsets$. Figure~\ref{fig:type-inference} gives the constraint generation rules for \Slice{}. We introduce a new judgment of form $C, \Gamma \vdash e : \tau$, which reads as \emph{in the environment $\Gamma$, $e$ has type $\tau$ and produces the set of constrains $C$}. Note that the inference rules formalize what constraint $C$ must be generated (and later solved) for a given expression $e$ to have inferred type $\tau$. 

Several constraint generation rules warrant special attention, which we now mention. In particular, the \textsc{TIf} rule uses the least upper bound operator $\latticesup$ to combine the value sets of the float-typed subexpressions in the two branches of the conditional. This ensures that the resulting value set of the entire entire conditional conservatively approximates all possible outcomes of the conditional expression, regardless of the branch taken at runtime. Figure~\ref{fig:lattice} shows how such elements in a value set are joined. Additionally, the constraints generated by the \textsc{TLess} and \textsc{TLessEq} rules directly correspond to the answerability conditions defined in Definitions~\ref{def:answers-less} and~\ref{def:answers-less-equal}. For example, the constraint $B = \; \clt{V}$ can be viewed as a formulation of the requirement that ``$B$ answers $\clt{V}$''.
